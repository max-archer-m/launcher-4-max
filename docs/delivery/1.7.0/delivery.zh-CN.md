# Launcher4Max 1.7.0 交付

> 语义源：英文。中文对应文档：本文件与 [delivery.md](delivery.md)。

> 本记录定义 1.7.0 的计划交付边界。它本身不授权生产实现、提交、推送、打 tag、产物移动、发布或公开发行；这些动作仍需单独授权。

## 版本意图

`1.7.0` 补齐既有产品契约与已交付实现之间的全部已知差异，并使项目达到首次公开发布所需的就绪状态。作者于 2026-09-17 确定版本大纲，分为三个已确认的部分：补齐未实现的契约内容、补齐发布前准备、以及在横屏的产品定义存在之前不将其纳入本版本。

作者于 2026-09-17 确认了范围裁决：用途受限的无障碍服务作为快捷操作迭代的一部分从仅 debug 源集移入 mainline；隐私联系资源中的过期仓库 URL 作为发布前准备修复；本版本的性能预期为作者主设备可跑通已验收的核心旅程，不追求数值性能门槛。

## 交付级别

`Formal release artifact`（正式发布物），定义见[发布治理](../../release.md)。本版本适用该级别的全部门槛，并显式提升一项：正式发布密钥（release keystore）在首个正式产物打包前必须满足安全存储与两份独立加密备份要求。Git tag、GitHub Release 与任何对外发布仍是单独授权动作，不属于版本完成范围。

应用身份为 `com.maxarchm.launcher`。`versionName` 为 `1.7.0`，`versionCode` `8` 按下一个未占用值分配，待标识符提升提交产生时记录。

## 纳入范围与用户旅程

在本版本完成时，作者可以通过专用的快捷操作设置子页，将 Home 基本信息区的两个快捷操作槽位分别绑定为 No action、Edit mode 或 Screen lock，绑定随手动备份文件保存；在无障碍服务关闭时绑定 Screen lock 会进入已披露的授权流程，且不改变已保存的绑定。无障碍服务以用途受限边界存在于所有构建类型中，因此被绑定的锁屏手势在 release 构建中可用。原独立的"双击锁屏" Settings 项被移除，隐私声明与无障碍披露改用"绑定手势"与"屏幕锁定"表述。

在 Home 上，当 Launcher4Max 不是默认启动器时，作者会在基本信息区与收藏主列表之间看到一张可关闭的默认启动器提示卡；其可见性每次进入前台评估一次，选择操作路由到与 Settings 默认主屏入口相同的系统目的地。应用名称与契约规定的提示文本以共享文本光晕替代字形阴影渲染，应用大小块呈现两条带校准视觉值的三档渐缩滑杆。

仓库持有发布治理所需的操作决策：APK 保留位置与策略、正式签名密钥的保管与备份流程、权威构建/签名/摘要/安装命令、tag 命名约定与分发渠道，并配有面向公众的 README、安装说明、截图与依赖许可清单。性能预期记录为主设备对核心旅程的验收。

- 超出迭代 34 所交付清单与处置范围的新第三方 License 呈现。

## 技术方案与风险

迭代 32 与 33 实现已验收的契约，实现细节由开发侧掌握。迭代 34 以一次经授权的产品契约变更（发行边界与性能预期记录）开始，随后进入操作工作；其契约基线按修订规则在作者验收该变更后更新。

主要风险：备份 schema 扩展必须保持旧备份在方向性兼容规则下可导入；以槽位解析替换硬编码的双击/长按手势不得回归编辑模式进入或失败 toast；无障碍服务 mainline 化会改动 release manifest，并需要 ADR-0004 改写为绑定驱动触发；文本光晕与渐缩滑杆的数值刻意未校准，需要作者设备校准后才能定稿其契约；被搁置的抽屉自动化测试簇核心正是滑杆拖拽注入，自定义滑杆的自动化覆盖存在该已知风险；发布门槛（密钥保管、摘要、可追溯性）属于流程工作，无法以代码替代。

## 依赖与顺序

迭代 32 必须在迭代 34 的操作工作之前完成：正式发布物必须包含在 release 构建中真实存在的锁屏能力，而只有 mainline 无障碍服务能提供。迭代 34 内部，产品契约阶段先于操作阶段。迭代 33 在代码与契约上均与两者独立、文件重叠低；按作者既有的单线惯例，三个迭代按记录顺序串行执行。此顺序不将工作绑定到分支、终端、贡献者或预测日期。

## 验证

本版本的强制验证环境为作者指定的主物理设备。迭代级验证遵循各迭代契约。版本完成另需满足发布治理的 `Formal release artifact` 门槛：确定的兼容环境、已执行且无未解决纳入路径失败的验证、依赖与许可处置、对发布构建的安全与隐私评审、稳定签名保管及其两份独立加密备份、产物摘要、外部保留与完整的源到产物可追溯性。性能按作者 2026-09-17 裁决以主设备对核心旅程的验收验证；不追求数值门槛。

## 产物与发布要求

验收 APK 必须保留 `com.maxarchm.launcher`，使用已验收的 `1.7.0`/`versionCode 8` 标识，可追溯到唯一源提交与签名类别，并支持自先前已安装版本所需的升级旅程。正式签名密钥在首个正式产物打包前必须满足安全存储与两份独立加密备份要求，任何私有签名材料不得进入 Git 或权威文档。保留产物存放于仓库之外作者指定的共享上下文中，复制后做 SHA-256 校验。打 tag、创建 GitHub Release 与任何上传仍是单独授权动作。
