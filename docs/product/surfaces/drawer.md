# Drawer Interaction Specification

> Public semantic source: English. Chinese counterpart: [drawer.zh-CN.md](drawer.zh-CN.md). Shared navigation is defined in [navigation.md](../navigation.md); exact Drawer visual values are defined in the [Drawer presentation specification](../presentation/drawer.md); the spatial sketch is the shared [Drawer wireframe](../wireframes/drawer.txt), with reading rules in the [wireframe index](../low-fidelity-wireframes.md).

## Purpose and layout

Drawer presents every launchable application entry successfully read from the sources exposed to the Launcher by the platform, including cloned entries. System and user-installed applications are treated alike.

“Every launchable application entry” is bounded by Launcher4Max's current Android role and least-privilege permissions. It does not mean every installed package, hidden profile, or entry that could become visible only after adding another sensitive permission.

- The application inventory supports a finite selected items-per-row count and is not restricted to one item per row. The current arrangement contract includes right-side-name, below-icon-name, and hidden-name label placement; it does not imply another named layout mode.
- With inline section anchors, each anchor occupies its own row and scrolls with the application list; it never remains pinned over later content. With left-side anchors, each anchor occupies the leading column beside its own application section. It pins immediately below the fixed top app bar while that section crosses the viewport and is pushed away by the next section anchor or the end of its owning section. At most one left-side anchor is pinned at a time; it never escapes its section, creates a separate viewport-wide panel, or becomes interactive. The Settings section uses a gear as its left-side anchor rather than fitting the localized `Settings` label into that column. Inline anchors add no permanent margin to application items.
- Right-side-name, below-icon-name, and hidden-name arrangements use the exact item geometry defined in the [Drawer presentation specification](../presentation/drawer.md#surface-and-application-content). The selected items-per-row count divides the available application-content width. Names occupy one static line and use end ellipsis; hidden-name arrangement renders no name.
- The application-size setting combines two independent three-tier selections — application icon size and application name (text) size — presented as two tapering sliders in one block titled `Application size · Text size`. Exact control geometry belongs to the [style settings panel presentation specification](../presentation/style-settings-panel.md).
- Selecting an application immediately launches it. Ordinary Drawer and search results share one surface-wide `600ms` rapid-activation window: the first accepted activation suppresses every later Drawer application activation until the window expires, regardless of identity.
- If an application launch handoff fails, Drawer keeps the current mode, query, anchor, and relative list position, shows the localized short Toast `Unable to open application`, and requests one non-blocking inventory refresh. The failure itself is not evidence of permanent disappearance. A failed refresh adds no second Toast or blocking state; later reliable inventory follows the ordinary refresh rules.
- Long-pressing an application produces the platform-standard long-press haptic. Releasing the pointer after that haptic opens the application action sheet; moving beyond the platform touch slop after that haptic instead begins [drag-to-favorite](#drag-to-favorite) on a drag-eligible item, as defined below.

## Drag-to-favorite

- Drag-to-favorite is available in ordinary Drawer Content and in search mode. It is unavailable in favorite multi-selection mode, Loading, and Error. The fixed Settings item never participates.
- An application item is drag-eligible only when its stable launchable identity is neither already assigned to any favorite module nor reliably disabled. A reliably disabled identity cannot enter favorites.
- After the long-press haptic, moving the pointer beyond the platform touch slop on a drag-eligible item begins drag-to-favorite; releasing without that movement opens the application action sheet.
- On an already-favorited identity, movement beyond the touch slop does not begin a drag: Drawer shows the localized short Toast `App is already in favorites`, and releasing the pointer still opens the application action sheet. On a reliably disabled identity, the same movement shows the localized short Toast `Unable to add to favorites` and release still opens the application action sheet.
- Drag-to-favorite adds no haptic beyond the one long-press haptic. The moving application lifts into a non-interactive preview that is the current real-time snapshot of its Drawer item and retains that source presentation until handoff to the destination.
- Drag recognition programmatically completes the downward Drawer-to-Home transition. Home enters edit mode with the style settings panel collapsed and the add-favorite entries visible, preserving the main list's logical scroll position, without a Toast or other entry feedback. Drawer does not remove the dragged item or close gaps while the transition is in progress.
- Home resolves the candidate destination exactly by its own edit-mode rules in the [Home interaction specification](home.md): insertion boundaries within the destination module, and a release onto a main-list add-favorite entry creating that entry's module type with the application as its first favorite. Trailing module add-favorite entries, the basic-information region, the edit dock, the system-protected area, and every region without candidate feedback remain invalid destinations. Hover feedback uses the existing insertion line and hover emphasis, and main-list vertical edge auto-scroll follows the shared Home movement rules.
- A valid release performs one atomic favorite mutation with the same persistence semantics as Home edit-mode application movement: identity uniqueness, insertion into the resolved destination order, and new-module creation belong to that single mutation. While the save is unresolved, the preview stays at its release position and success replaces the preview with the saved destination application. Regardless of outcome, Home exits edit mode immediately when the atomic operation completes. Success shows no additional feedback; save failure restores the last reliably persisted complete favorite state and shows the localized short Toast `Unable to save favorite`.
- Releasing in an invalid region, pointer cancellation, or system Back cancels drag-to-favorite without a favorite mutation, does not return to Drawer, and leaves normal Home with edit mode exited. No cancellation or invalid path shows a Toast or Snackbar.
- The Android system Home action and external interruptions during the journey follow the Home edit-mode interruption rules: the movement is cancelled, edit mode is exited, and normal Home is displayed.
- Beginning drag-to-favorite from search mode leaves Drawer through the same programmatic downward transition and clears the transient search query and mode under the existing search-exit rule; the next ordinary Drawer entry starts outside search.
- Beginning drag-to-favorite suppresses application activation for that pointer sequence; a release is a destination decision, never a launch. The `600ms` rapid-activation window is otherwise unaffected.
- A completed drag-to-favorite is a committed favorite mutation and invalidates the latest-removal Undo snapshot through the existing Home rule.

## Top app bar

- Drawer always reserves one fixed top app bar below the status-bar safe inset. It remains fixed while the application list scrolls, uses the selected Drawer background without a separate visible bar background, and does not introduce an independent bar surface. Exact geometry belongs to the Drawer presentation specification.
- In ordinary Content, the left side contains the standard Back control. Selecting it completes the same downward Drawer-to-Home transition as system Back. The center contains the application search field, and the right side contains one overflow-style display-settings entry in its own interaction target. Search-field geometry and visual states belong to the Drawer presentation specification.
- The application list and AlphabetIndex begin below the top app bar and remain clear of
  its controls. The fixed bar height participates in the available-height calculation
  for the index.

## Application search

- Search is available only in ordinary Drawer Content. Favorite multi-selection does not expose search. Loading and Error do not display the search field because no reliable application list is available to filter.
- The ordinary field shows a leading magnifying-glass symbol and the localized hint `Search apps`. Selecting the field enters search mode in place, focuses text input, and requests the software keyboard without navigating to another surface.
- Search mode hides the ordinary Back and display-settings controls. Their layout is replaced by an empty physical-left reservation and a physical-right localized `Cancel` action so the field remains horizontally centered. The active search boundary remains highlighted whenever search mode is active, including while the query is empty or the keyboard is hidden.
- Results update after every query-text change. Search has no submit button, Return-triggered search, or product-level delay. An IME Search, Done, or Return action does not create a second submission path.
- Before matching, leading and trailing query whitespace is ignored. An empty or whitespace-only query presents the complete application inventory. Latin matching uses contiguous containment after the same case-insensitive and diacritic-insensitive normalization used by Drawer ordering. Han text and other text match contiguous characters from the displayed application name. Character skipping, edit-distance correction, Han-to-Latin query matching, pinyin, pinyin initials, package names, historical names, and hidden metadata are outside the current search contract.
- Filtered applications retain the selected Drawer icon size, name (text) size, name placement, items-per-row count, section-anchor presentation, and existing complete-name order. Search does not introduce relevance ordering. Section anchors and AlphabetIndex are rebuilt from only the non-empty filtered application sections. The fixed Settings section and Settings index gear are hidden throughout search mode because search filters applications only.
- Every contiguous matched span in the displayed application name uses the presentation-defined search emphasis without changing the complete name, item geometry, line count, ellipsis rule, or ordering. Accessibility exposes the complete application name once rather than separate nodes for highlighted and unhighlighted spans.
- A non-empty query shows a trailing X clear action. Selecting it clears the query, keeps search mode, focus, keyboard eligibility, and highlighted search boundary active, presents the complete application inventory from its content start, and removes match emphasis. The clear action is absent while the query is empty.
- If no application matches, the application region displays the localized message `No matching apps`. This is an ordinary empty search result, not Loading or Error: Retry, application items, section anchors, AlphabetIndex, Settings section, and Settings gear are absent, while the search field, clear action when applicable, and `Cancel` remain available.
- Entering search records the ordinary list anchor and relative position. Selecting `Cancel` or pressing system Back exits search once, hides the keyboard, clears the query and emphasis, restores the complete ordinary Drawer including Settings and its index gear, and restores the recorded ordinary position. That Back activation does not continue through Drawer-to-Home. An IME-specific hide-keyboard action only hides the keyboard and preserves search mode, query, results, and boundary emphasis; selecting the field can request the keyboard again.
- The search field exposes its localized search label and editable value. The X is one `Clear search` accessibility action and `Cancel` is one exit-search action; the decorative magnifying glass has no separate focus target. Search mode remains semantically identifiable without relying only on boundary color, and result-count changes use ordinary collection updates rather than repeated Toast, Snackbar, or assertive announcements.
- Launching a result follows ordinary application launch. Leaving Drawer, launching an application, or process recreation clears the transient search query and mode; the next ordinary Drawer entry starts outside search. Reliable inventory changes received during search reapply the current query to the latest reliable inventory without changing the query. Existing inventory identity, partial-read, and destructive-reconciliation rules remain authoritative.

## Display settings

- Selecting the ordinary-mode display-settings entry opens one modal Drawer display-settings panel. The modal layer blocks the underlying Drawer; system Back or selecting outside the panel closes it without invoking a separate confirmation action.
- The panel owns four independent semantic settings: application size, application arrangement, section-anchor presentation, and Drawer background. Application size combines two independent tiers — application icon size and application name (text) size — and each tier has exactly `Large`, `Medium`, and `Small`, with `Medium` as the current default for both.
- Application arrangement combines a three-option label-placement selector, `Right`, `Below`, or `Hidden`, with an independently operated items-per-row stepper. The current default is `Right` with one item per row, matching the representative default Drawer wireframe. Every icon and text tier combination supports the same fixed count bounds: `Right` allows one or two items per row, `Below` allows one through four, and `Hidden` allows one through six. Decrement is disabled at one; increment is disabled at two for `Right`, four for `Below`, and six for `Hidden`, and neither action can cross its current placement boundary. Changing the count never changes label placement. Changing from `Right` to `Below` preserves the current count of one or two and recomputes stepper availability; at two, increment therefore changes from disabled to enabled. Changing from `Below` to `Right` preserves one or two, but atomically clamps three or four to two; increment is then disabled. Changing to `Hidden` preserves the current count of one through four and raises the maximum to six, so increment becomes available below six. Changing from `Hidden` to `Right` atomically clamps a count above two to two, and changing from `Hidden` to `Below` atomically clamps a count above four to four. The placement change and any required clamp form one complete display-setting change and one save. `Hidden` hides only the displayed name: accessibility still announces the complete application name, and search still filters by it. Changing either size tier preserves the selected count because every tier supports the same bounds. Available width never raises these product-defined maxima.
- Section-anchor presentation has exactly `Inline` and `Left side`; the current default is `Inline`. Each outcome retains its own scrolling or section-bounded pinning behavior defined above, and both remain non-interactive.
- The Drawer background is one continuous setting selected on a slider: an integer percentage from `0` through `100`. The selected percentage defines one full-surface background layer whose opacity equals that percentage; `0` leaves the wallpaper clear, and `100` presents the solid background color defined by the presentation specification. The background never applies blur, never samples the wallpaper, and never varies by list or pointer position. The presentation-defined fixed text and monochrome-artwork shadows remain in effect at every percentage. A fresh configuration defaults to `50`.
- The background slider exposes the continuous range from `0` through `100`; its value is a whole percentage with no finer granularity, a tentatively accepted value. The slider uses the platform-standard continuous progress presentation without tick marks, and the current percentage is displayed in the fixed-width readout defined by the presentation specification. Accessibility exposes the localized background-opacity label, the current percentage value, and the standard localized range actions, each adjusting the value by `1`. Each whole-percentage value change during a touch drag produces one short tick haptic; no other slider feedback exists beyond the readout and the background itself.
- The two application-size sliders expose three snapping stops each — `Large`, `Medium`, and `Small` — and follow the background slider's drag path: a touch drag or a stop tap previews the resulting sizes continuously without changing the committed display-setting state and commits once at pointer release. Each tier change during a touch drag produces one short tick haptic. While the name placement is `Hidden`, the text-size slider uses the shared disabled opacity, rejects activation, and reports unavailable; the icon-size slider remains available, and selecting another name placement restores the text-size slider with the persisted text tier.
- Every valid change in any of the four setting groups applies immediately to the current Drawer and starts an immediate local save of the complete display-setting state. Dragging the background slider and dragging either application-size slider are the exceptions: the drag previews the resulting appearance continuously without changing the committed display-setting state and starts no save. Releasing the pointer commits the released value as one valid change—unless it equals the currently persisted value, in which case no change and no save occur—and starts one display-setting save. Pointer cancellation, panel closure, the system Home action, an external interruption, or process death that ends the gesture before pointer release commits nothing and starts no save: Drawer immediately reverts the background, its percentage readout, and both application-size sliders to the last successfully persisted complete display-setting state without a Toast, error, or other feedback. Only one display-setting save may remain unresolved at a time; another setting change cannot begin until that save resolves. No group uses a separate Confirm action. When changed geometry invalidates the exact list position, Drawer keeps the formerly topmost visible application and its relative offset when possible, otherwise clamping to the nearest valid position.
- Saving and panel dismissal are independent atomic operations. System Back or selecting outside the panel remains available during saving; closing the panel neither confirms again, discards the applied candidate, nor cancels its unresolved save.
- A successful save becomes the latest durable display-setting state and survives panel dismissal, Drawer closure, process recreation, and device restart. Success does not reopen a dismissed panel. Drawer applies the durable state before presenting ordinary Content rather than visibly presenting defaults first and then relaying out. Clearing Launcher4Max application data or uninstalling Launcher4Max removes the state; the next installation or launch after clearing starts from the confirmed defaults.
- Each user change is atomic across the complete display-setting state. If its save fails, Drawer restores the complete previous successfully saved state and shows the localized short Toast `Unable to save display settings`. An open panel refreshes in place to that restored state; a dismissed panel remains dismissed and is not reopened. The failure does not open Error, leave a session-only candidate appearance, change favorites or inventory order, or block application launching. A later valid change can retry through the same behavior.
- When an existing installation first reads a product version containing a newly introduced display-setting field, every readable existing field is preserved and each absent field receives its current default. An absent Drawer-background-opacity field therefore resolves directly to the default `50`, without a special compatibility branch, migration prompt, or separate notice; the prior background-mode choice between the transparent and frosted-glass presentations is not mapped to a percentage. An existing legacy application-size field populates both the icon-size and application-name-size (text-tier) fields; when neither size field exists, both resolve to `Medium`.
- Each selector is one accessibility control that exposes its label, complete option names, current selected state, and enabled state. The items-per-row control exposes the current numeric value and separate localized decrement and increment actions; a disabled boundary action is reported as unavailable and does not change the value.
- The background slider exposes its localized label, the current percentage value, and the standard localized range actions, each range action adjusting the value by `1`.
- Each application-size slider exposes its localized label — `Application size` for the physical-left slider and `Text size` for the physical-right slider — the current tier name, and the standard localized range actions, each moving one tier; a disabled text-size slider reports unavailable and does not change the tier.
- A selector change is atomic. While its selection animation is active, the display-settings panel ignores additional click activations so two visible selections cannot compete. While any display-setting save is unresolved, every setting-mutation control rejects activation and exposes disabled semantics. These temporary locks preserve the current colors and opacity without greying out controls; the panel shows no Loading state or progress indicator. Count-boundary actions retain their ordinary unavailable presentation. System Back and outside-panel dismissal remain available in both intervals.
- Host-specific panel placement belongs to the [Drawer presentation specification](../presentation/drawer.md#display-settings); shared panel-surface, setting-row, selector, stepper, animation, and target geometry belongs to the [style settings panel presentation specification](../presentation/style-settings-panel.md).

## Favorite multi-selection mode

- Selecting a Home edit-mode add-favorite entry opens the existing Drawer surface in favorite multi-selection mode and captures its persisted or provisional vertical-module or ribbon destination. Drawer completes the upward transition programmatically.
- The same inventory, locale-aware ordering, application items, section anchors, and AlphabetIndex are reused. The fixed Settings section and Settings index token are hidden because Settings is not a selectable application target.
- The top app bar replaces ordinary contents with `Cancel`, a localized captured-destination description, and `Confirm`. The description distinguishes adding to or creating a vertical module from adding to or creating a ribbon without assigning a persistent name or ordinal. The originating add-favorite entry's position alone determines whether the captured destination is an existing module or a new one; no panel state or prior selection participates. Confirm is disabled while nothing is selected.
- Selecting an available application toggles its selection instead of launching it. Long-press actions and the application action sheet are disabled in this mode. Selection items reuse the ordinary inventory's items-per-row grid and arrangements without layout change. An available unselected item shows no selection indicator; the mode is expressed by the top app bar. A selected item receives the selected-item treatment defined by the Drawer presentation specification: the item scales to approximately ninety percent as a purely visual transform with unchanged layout bounds, gains the complete selection outline, and carries one overlaid order badge at its top-left corner showing its one-based plain-text order. The badge is not independently interactive; selecting the complete item again deselects it, removes selected treatments, and closes later numbering gaps.
- Selection order is the order in which entries were selected. Deselecting an entry immediately closes the numbering gap, and confirming appends the remaining entries to the captured destination in the displayed number order.
- An identity already assigned to any favorite module remains visible but unavailable for selection. Its icon and name use disabled semantic opacity, and it receives no badge, outline, or scaling; selecting it has no effect and produces no feedback. Primary, cloned, and work-profile entries remain distinct identities.
- Home does not pre-check whether this mode will contain an available identity. If every visible identity is already assigned, all items follow the unavailable treatment and Confirm remains disabled; Drawer adds no separate full-favorites state, Toast, or redirect.
- Selecting Confirm saves the complete current selection once, then completes the downward transition and returns to the same Home edit mode. Home restores the favorite main list and every existing ribbon to their recorded pre-entry scroll positions without automatically scrolling to, centering, or revealing the changed destination or newly added entries. The destination and main-list content extents grow naturally after the saved addition; added content may therefore remain outside the current viewport until the user scrolls to it.
- Selecting Cancel, system Back, or a valid downward Drawer dismissal discards the complete unconfirmed selection, completes the downward transition, and returns to Home edit mode with the favorite main list and every existing ribbon at their exact pre-entry scroll positions. Cancellation does not create a destination, change a content extent, or redirect the user to another module.
- The Android system Home action also discards the complete unconfirmed selection but exits Home edit mode and resolves directly to normal Home, except that it does not cancel an atomic save already in progress. No cancellation path persists a partial selection, and the downward animation itself never implies confirmation.
- Inventory changes reconcile against stable entry identity without interrupting multi-selection. A newly installed entry appears unselected. A selected entry whose name or icon changes updates in place while retaining its selection number. Temporary profile unavailability or a partial inventory-read failure retains the affected entry and selection rather than treating it as permanently absent. These non-destructive changes show no additional feedback.
- When a refresh confirms that a selected application was uninstalled, a clone was removed, or another launchable identity permanently disappeared, Drawer silently removes that item from the current selection and closes later numbering gaps. An unselected identity confirmed absent simply disappears. Neither case shows a Toast, Snackbar, Dialog, or other explicit notice.
- Confirm revalidates the selection against the latest reliable inventory and silently excludes identities confirmed permanently absent. Remaining valid identities are saved atomically in their displayed order. If none remain, Confirm performs no write and follows the ordinary confirmed downward return to Home edit mode without additional feedback; this race does not introduce a separate validation or disabled-button state. The existing rule that Confirm is disabled while the visible selection is already empty remains unchanged.
- The first valid Confirm activation starts one exclusive atomic save and suppresses duplicate activation. Until it resolves, the visible selection remains in place, Confirm is disabled, and Cancel, item selection, AlphabetIndex input, valid downward dismissal, and system Back do not act. The surface shows no full-screen Loading state, progress indicator, or cleared selection. Inventory changes received during this interval are queued for reconciliation after the save resolves rather than changing the submitted snapshot.
- Save success performs the downward transition exactly once and returns to the originating Home edit mode when it remains active. Save failure retains the current still-valid identities and order and follows the existing retry behavior below: all multi-selection interactions return when reliable inventory remains available; if a full inventory failure is still active, Drawer instead presents the multi-selection Error state with only its defined recovery and cancellation paths. The Android system Home action may background Launcher4Max but does not cancel an in-progress save: success remains persisted, while failure never claims completion and the next Launcher4Max entry presents the last successfully persisted favorite state.
- The complete application item exposes one toggle-selection accessibility node named by the application. Its state reports `Not selected` or `Selected, item N`; renumbering updates that state. An already-favorited item reports `Already in favorites, unavailable for selection` and disabled state. The order badge exposes no second focus target or duplicate description. Silently removing a permanently absent selection does not add a long announcement; platform focus recovery may move to the nearest remaining valid item.
- If saving fails, Drawer stays in multi-selection mode, retains the current valid identities and order, and uses the [Home failure contract](home.md#loading-inventory-changes-and-failure). Reliable inventory permits retry or cancellation; unavailable inventory disables Confirm until Retry restores Content while cancellation remains available. No partial selection is persisted.
- If the captured destination becomes invalid before mutation, Drawer discards the complete unconfirmed selection and never redirects it to another module or substitute destination. A persisted reference becomes invalid when its module is removed. A provisional reference remains valid while its originating session and Home edit context remain active; having no current selection, no persisted module, or no currently eligible identity does not invalidate it. Replacement of the session or termination of the edit context invalidates it. Applicable failure returns to the active Home edit context with Home's non-blocking save feedback.

### Availability states during multi-selection

- Entering favorite multi-selection while inventory is Loading still opens the captured multi-selection context. The top app bar keeps `Cancel` and the destination description, disables Confirm, and the application region uses the existing Loading presentation. Application items, Settings, and AlphabetIndex remain absent. Cancellation returns to the captured Home edit viewport without creating a destination or changing favorites.
- A full inventory failure after one or more selections preserves those identities and their order only in the current in-memory selection, hides the unreliable application list, disables Confirm, and uses the existing Error presentation and Retry action. Cancel, system Back, and valid downward dismissal remain available and discard the selection normally. The failure neither submits nor clears the selection and does not infer that its identities permanently disappeared.
- Retry performs one read and first returns the application region to Loading. Success restores Content, application anchors, and AlphabetIndex from the latest reliable inventory. Still-valid selections retain their order; confirmed permanently absent identities are silently removed and later numbers close their gaps; temporarily unavailable identities remain selected. Confirm then follows the resulting selection state naturally. Drawer restores the pre-failure anchor and relative position when valid; otherwise it uses the nearest valid position. Recovery adds no success Toast or Snackbar.
- Retry failure returns to the same Error presentation, preserves the in-memory selection, and adds no repeated Toast, Snackbar, Dialog, or stacked error layer. Retry and ordinary cancellation paths remain available. Every Retry is read-only with respect to favorites and starts only one inventory read.
- A reliable inventory in which every launchable identity is already favorited remains ordinary Content rather than Empty or Error. The complete sorted and anchored application list and AlphabetIndex remain available, every item uses the existing already-favorited disabled presentation, and Confirm remains disabled. No dedicated explanatory message is added.
- A reliable inventory with no launchable application entry reuses the existing Error presentation rather than introducing a multi-selection Empty state or dedicated copy. Settings and AlphabetIndex remain absent, Confirm is disabled, and Cancel, the destination description, Retry, system Back, and valid downward dismissal retain their existing behavior.
- An inventory failure received after an exclusive atomic save starts is queued like any other inventory change and does not replace the frozen save surface, cancel the submitted snapshot, or cause another validation pass. Save success completes the normal return and then reconciles the latest inventory. Save failure restores the selection; if reliable inventory is still unavailable, it then enters the multi-selection Error state above. No additional feedback is layered over the existing save-failure or inventory-error feedback.

## Profile and Private Space boundary

- Ordinary, work-profile, and cloned launchable entries follow the existing inventory, identity, sorting, launch, favorite, and refresh rules when Android normally exposes them to Launcher4Max without hidden-profile access.
- The current product does not support Android Private Space and does not declare `ACCESS_HIDDEN_PROFILES`.
- Launcher4Max does not actively query, access, display, deduplicate, sort, launch, favorite, or restore state for Private Space entries that require hidden-profile access.
- Launcher4Max does not provide a separate Private Space container or controls to show, hide, lock, unlock, favorite, or restore Private Space state.
- Absence of Private Space entries under this boundary is expected product behavior, not an incomplete Drawer inventory or loading error.
- Platform exposure of ordinary, work-profile, or cloned entries does not classify those entries as Private Space and does not remove them from the current contract.
- Future Private Space support is a separate product capability. It requires a new project-author decision and renewed review of product interaction, permissions, privacy, compatibility, and validation before it can enter the current contract.

## Grouping and sorting

- Sorting derives a normalized sort form from the complete displayed application name before applying Android's locale-aware collation for the current system locale. The displayed name itself is not changed.
- The normalized sort form uses platform-provided Han-to-Latin transliteration, removes Latin diacritic differences, and ignores case. Han names and names already written with Latin characters therefore participate in one mixed ordering rather than separate script blocks.
- Platform transliteration determines pinyin and polyphonic-character results. Launcher4Max does not ship or maintain an independent pronunciation dictionary, pinyin library, or Launcher-defined character-priority table.
- Section assignment follows the same normalized complete-name sort form rather than inspecting only the first raw Unicode character of the displayed name.
- Entries that the normalized locale-aware sectioning cannot place under Latin A-Z are grouped under `#`; their internal order uses the same complete-name comparator. Launcher4Max does not separately rank numbers, punctuation, Emoji, or other scripts inside `#`.
- Every application participates in the same ordering regardless of whether it is a system, downloaded, primary, or cloned application.
- When displayed names collate equally, identity precedence is primary application, cloned application, then work-profile application.
- When both displayed-name collation and identity category are equal, use a stable launchable-entry identity as the final tie-breaker. The observable order must remain stable across refreshes; the product contract does not prescribe the implementation field or API.
- After every application section, the Drawer list ends with a fixed independent section headed `Settings`. This heading is an anchor in the same list, but it is not an application section and does not participate in application sorting.
- The fixed Settings section contains one clickable item with a Settings gear icon and the name `Settings`. Only selecting this item opens Settings.

## Alphabet index

- A fixed right-side index is visible whenever Drawer presents navigable Content. Full-surface Loading and Error states hide the entire index because those states do not present any list anchors; the index is not partially displayed.
- It contains `#`, each non-empty A–Z section, and a fixed Settings gear below Z. Empty alphabetical sections are omitted.
- Index labels, slots, and Settings gear use the exact values defined by the [Drawer presentation specification](../presentation/drawer.md#section-anchors-and-alphabet-index). The complete slot and index interaction range must not be reduced to the gear artwork, and non-empty entries are not stretched to redistribute unused height.
- The maximum index model contains 28 slots: `#`, A–Z, and Settings. Its minimum complete available height is therefore `560dp` after excluding status-bar, navigation-bar, display-cutout, Drawer-padding, and system-gesture insets.
- At `560dp` or more of available height, the index does not scroll. Below `560dp`, the index becomes an independently scrollable vertical region while the application list remains separately scrollable.
- On initial pointer down over an available index entry, the application list jumps immediately and without animation to that entry's anchor, with the anchor heading positioned at the top of the visible list. This direct positioning does not wait for pointer release and produces index-step haptic feedback.
- After the initial pointer down, entering a different available index entry starts a smooth scroll to that entry's anchor. Moving within the same index slot does not change the list position. A newly selected anchor cancels and replaces an unfinished smooth-scroll target; targets are never queued.
- The final position is the last selected anchor position. On pointer release or cancellation, the current smooth scroll finishes at that anchor; the list does not derive a percentage position from the pointer, snap to another anchor, or play a completion animation.
- A magnified bubble displays only the active character or Settings gear using the Drawer presentation specification. It remains visible while the pointer is held and disappears immediately on release or cancellation.
- While the index owns the pointer, the application list does not independently consume the gesture; index movement may drive the list only through the discrete anchor smooth-scroll behavior above.
- The Settings gear is an index anchor, not a control that opens Settings. Selecting it by initial pointer down jumps immediately to the fixed Settings section; entering it during index movement smooth-scrolls to that section and produces the same index-step haptic feedback as any other anchor change.
- The Settings item in that section is the only Drawer control that opens Settings.
- Returning from Settings preserves the Drawer list position during the same process.
- TalkBack semantics and an accessibility-specific alternate index interaction are outside the current personal-use scope.

## Inventory changes and states

- The inventory updates while Drawer is active when applications or cloned entries are added, removed, enabled, disabled, or renamed.
- Inventory changes observed while an ordinary external application is active are reconciled without presenting a new Loading state on return to Home. When Drawer is next presented, it uses the reconciled inventory and applies the current anchor and position rules.
- If a non-current ordinary, work-profile, or cloned profile read fails while another profile provides usable entries, Drawer presents those available entries as Content rather than blocking the entire surface. Entries from the failed profile may be absent, and the current product does not require a partial-read warning.
- A partial profile failure must not crash Launcher4Max, prevent available entries from launching, or be treated as confirmation that an unavailable entry was permanently removed. A failure that leaves no usable inventory follows the Error state below.
- The intentional absence of Private Space entries under the current product boundary is not an inventory failure.
- A routine live update preserves the current section anchor and the relative scroll position within that anchor whenever the anchor still exists.
- If the current anchor disappears, move to the next existing application anchor in sort order and position its heading at the top of the visible list. An Inline heading then scrolls normally; a Left-side heading follows its ordinary section-bounded pinning behavior.
- If no later application anchor exists, remain at the bottom of the application list without automatically moving into the Settings section. The Settings anchor is not an application anchor, and an inventory update never opens Settings.
- An update never automatically launches an application or opens an application action sheet or Settings.

### Loading

- While no usable inventory result is available and a read is in progress, the application region shows a progress indicator and the localized message `Loading applications…`.
- Loading is an in-progress state, not an empty or error result. The error icon and Retry action are not shown concurrently with the progress indicator.
- The application list, fixed Settings section, and AlphabetIndex are absent for the full duration of this state.

### Empty or failed result

- A successful read that returns no launchable entries is treated as an error rather than a valid empty Drawer.
- A failed inventory read that leaves no usable launchable entries uses the same error state.
- The application region hides the progress indicator, shows the shared non-interactive status icon, displays the localized message `Unable to load applications`, and provides a separate `Retry` action.
- The error state does not instruct the user to restart Launcher4Max.
- The application list, fixed Settings section, and AlphabetIndex remain absent while this full-surface error is shown.
- Selecting Retry clears the visible error state, returns to the Loading state, and starts a new inventory read.
- While the user remains on the same Error presentation, activity resume, network changes, package callbacks, and other ordinary lifecycle events do not automatically retry or clear the error. Leaving Drawer and later entering it again starts a new initial read.
- A successful retry displays the application list. An empty or failed retry returns to the same error state.

## Acceptance intent

- Ordinary Drawer keeps the top app bar fixed and visually transparent over the selected Drawer background while content scrolls; its Back arrow returns through the normal downward transition, its centered search field enters in-place application search, and its right-side display-settings entry opens the display-settings dialog.
- Search filters on every text change through the confirmed contiguous matching rules, preserves the selected Drawer arrangement and complete-name order, rebuilds anchors and AlphabetIndex from matching application sections, hides Settings, distinguishes no-match Content from inventory Error, and restores the recorded ordinary position only when search is cancelled or exited through system Back.
- Ordinary and search-result application launches use the same `600ms` surface-wide rapid-activation window. Launch failure preserves the complete current Drawer context, provides one short failure message, and starts one non-blocking refresh without inferring permanent disappearance or stacking another failure surface.
- Drawer display settings expose only the four defined setting groups and their defined options. Confirmed defaults are Medium application icon size, Medium application name (text) size, Right-side names, one item per row, Inline section anchors, and a Drawer background opacity of `50`. Right-side names allow one or two items per row, below-icon names allow one through four, and hidden names allow one through six at every icon and text tier combination, with boundary actions disabled. Count changes never select another placement; switching to `Below` preserves one or two and enables increment at two, switching to `Right` atomically clamps three or four to two and disables increment, switching to `Hidden` preserves one through four and raises the maximum to six, and leaving `Hidden` clamps the count to the destination placement's boundary. Every valid change applies and saves immediately; the background-slider and application-size-slider drags preview without persisting, commit and save once on pointer release, and revert immediately to the persisted state when interrupted before release. Only one save and one user change may remain unresolved, while dismissal stays available and never cancels that save. Success survives recreation and restart; failure restores the complete previous successfully saved state without reopening a dismissed panel. A newly introduced absent field receives its current default.
- Favorite multi-selection preserves selection order visibly through overlaid order badges on scaled, outlined items, never launches or long-presses an application, never exposes Settings, and saves only the complete selection through Confirm. Confirmation returns to the recorded Home edit position without automatically revealing changed content; every cancellation path discards all unconfirmed entries and restores the recorded main-list and ribbon positions.
- Every launchable entry returned by a successfully read source within Launcher4Max's current role and least-privilege boundary appears once. Entries from an isolated failed non-current profile may be absent without blocking available Content. Primary, work-profile, and cloned entries follow the applicable platform identity treatment; Private Space entries requiring `ACCESS_HIDDEN_PROFILES` are intentionally absent. Primary and cloned entries remain distinguishable when the platform supplies a badge; Launcher4Max-specific fallback distinction is outside the current scope.
- Initial index contact lands immediately on the intended anchor with its heading positioned at the top of the visible list. Each later available-token change smooth-scrolls to that token's anchor without queuing targets.
- Releasing or cancelling an index gesture leaves the application list at the last selected anchor; it does not preserve an arbitrary pointer-percentage position or snap elsewhere. The heading then scrolls normally with the list.
- Index gestures do not independently scroll the list or trigger application-item actions.
- Live inventory updates do not leave a removed application launchable from stale UI.
- Repeated refreshes with unchanged input preserve application ordering and the current anchor-relative position.
- After the long-press haptic, release opens the application action sheet and movement beyond the touch slop begins drag-to-favorite on eligible items in ordinary Content and search results. Ineligible items ignore movement with the defined short Toast and still open the action sheet on release. A recognized drag slides Drawer away programmatically, enters Home edit mode with the preserved list position, resolves the destination through the existing edit-mode rules, commits one atomic favorite mutation on a valid release, and always exits edit mode immediately after that operation. Invalid releases, cancellation, and Back leave normal Home without favoriting and without returning to Drawer.
